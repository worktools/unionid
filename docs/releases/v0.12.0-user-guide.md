# v0.12.0：用 ADT 安全领取任务与执行原子写入 / Safe ADT task claims and atomic writes

## 中文说明

### 这个版本解决什么问题

[下载 v0.12.0](https://github.com/worktools/unionid/releases/tag/v0.12.0)。UnionID 是一个面向单机应用状态的 Rust 数据库：用 struct/enum 描述数据，用 pipeline 查询和修改，持久化使用 redb。

v0.12 让“必须修改到指定数量的行”成为同一个请求中的成功条件。典型场景是领取待处理任务、按版本修改配置，以及需要两步都成功的业务写入。以前，合法的 update 即使命中零行也可以成功；现在可以紧接一条 `expect affected == 1`，条件不成立就回滚整个脚本。零行更新本身仍然合法，是否要求命中由应用决定。

### 安装并确认版本

原生包提供 Linux x86_64 和 macOS Apple Silicon 二进制，附带文档、示例和校验文件。选择对应平台，核对发布页 SHA-256 后解压，把包内 `bin` 加入 PATH。也可以用 Rust 1.94 或更高版本安装：

```bash
cargo install unionid --version 0.12.0 --locked
unionid version --format json
unionid docs query
```

`version` 应显示 `software_version: "0.12.0"`。`docs query` 是当前二进制自带的查询参考，包含 atomic-claim 示例，适合直接交给 LLM。首次使用可从 [五分钟入门](https://github.com/worktools/unionid/blob/v0.12.0/docs/GETTING_STARTED.md) 生成含 migration 的项目。

### 从空目录完整试一次任务领取

以下文件放在一个新的试验目录中，不操作已有数据库。把下面保存为 `setup.unid`：

```unid
enum State {
  Pending
  Running {worker: text}
  Done
}

struct Job {
  id: int
  state: State
  version: int
}

table jobs: Job {
  key id
}

insert jobs {
  id: 1
  state: Pending
  version: 0
}
```

`State` 是真实的和类型，只有 Running 带 worker；Job 是积类型。赋值位置已经知道类型是 State，因此 Pending 和 Running 可以省略 `State::`。

把下面保存为 `claim.unid`：

```unid
update jobs
filter id == 1 && version == 0 && state == Pending
set {
  state = Running {worker: "worker-1"}
  version = version + 1
}
returning {id, state, version}
expect affected == 1
```

执行：

```bash
unionid run --db jobs.redb --file setup.unid
unionid run --db jobs.redb --file claim.unid --format json
unionid run --db jobs.redb --query 'from jobs' --format json
```

首次领取返回 `ok: true`、`affected_rows: 1`，行中 state 为 Running、worker 为 worker-1、version 为 1。`returning` 后面的守卫不会吞掉返回行。JSON 的逐语句摘要为：

```json
[
  {"index": 1, "kind": "update", "affected_rows": 1},
  {"index": 2, "kind": "expect"}
]
```

再执行一次相同的 claim 命令：因为任务已经不是 Pending 且 version 已变化，命中零行，返回 `E_EXPECTATION`、`statement_index: 2`，CLI 退出码为 3。重新查询仍是 worker-1/version 1，不会产生第二次修改。真实应用把 id、预期 version 和 worker 换成 prepared 参数，避免拼接用户输入。

### 两步写入：验证后一条失败也能撤销前一条

金额示例使用整数最小单位，目的是展示回滚，不代表完整的财务模型。保存为 `accounts.unid`：

```unid
struct Account {id: int, balance: int}
table accounts: Account {key id}
insert many accounts [{id: 1, balance: 100}, {id: 2, balance: 0}]
```

保存为 `transfer.unid`：

```unid
update accounts
filter id == 1 && balance >= 50
set balance = balance - 50
expect affected == 1

update accounts
filter id == 99
set balance = balance + 50
expect affected == 1
```

```bash
unionid run --db accounts.redb --file accounts.unid
unionid run --db accounts.redb --file transfer.unid --format json
unionid run --db accounts.redb --query 'from accounts | sort id'
```

第二步找不到 id 99，报 `E_EXPECTATION`、`statement_index: 4`。即使第一步已在候选状态扣款，整个请求仍会回滚，两个账户余额仍为 100 和 0。把文件里的收款人 99 改成 2，再用同一条 `run --file` 提交整个文件：成功后余额为 50 和 50，摘要按源码顺序记录两条 update 与两条 expect。

**原子边界是一次请求。** 不要把扣款和入账拆成两次 CLI 调用或两条网络请求；已经提交的前一个请求不会被后一个请求的失败撤销。交互 REPL 中也不要先提交第一步，再输入第二步；多步业务操作用一个文件或完整 request 提交。

### 应用接入、重试与结果判断

Rust 嵌入式应用可用 `Engine::prepare` 和 `execute_prepared`，查询中的 `$sender`、`$recipient`、`$amount` 由 typed 参数绑定。内联 `queries!` 宏和静态查询绑定支持一条 DML 加尾随守卫；多条写入使用 Engine/prepare 或完整 CLI/TCP/HTTP 请求。[应用数据边界](https://github.com/worktools/unionid/blob/v0.12.0/docs/APPLICATION_DATA.md) 介绍原生 Rust ADT 的传入与解码。

网络应用遇到超时或断线时，不能只凭“没收到响应”判断回滚。请求可能已经提交。需要幂等重试时，为同一业务操作提供稳定的 `idempotency_key`，重试保持相同 query、参数和协议版本；可以改变用于关联尝试的 request_id。成功后的相同 key/digest 会重放原结果与逐语句摘要，避免重复写入；同 key 不同内容会冲突。失败请求不占用该 key。单独给每次尝试生成新 key 无法解决响应丢失后的重复执行。

处理结果时：

| 情况 | 应用应了解什么 |
| --- | --- |
| `ok: true` | 请求成功；读取 returning/final query 的 rows，以及 statements 中每条操作的命中数 |
| `E_EXPECTATION` | 行数不符合业务要求，整个脚本回滚；用 statement_index 找到失败守卫，再查询状态决定是否重新发起业务操作 |
| `E_EXPECTATION_CONTEXT` | 守卫位置不合法；修正脚本，不要原样重试 |
| 没收到完整响应 | 提交结果可能未知；用原幂等 key 和原请求重试确认 |

`statement_index` 从 1 开始，按顶层语句计数；filter/set/returning 是 update 的 stage，不各占一个序号。失败不会返回未提交的 rows/摘要。成功脚本最后如果还有查询，顶层 rows 来自最终查询；顶层 affected_rows 不能当作整个脚本的修改总数，要查看 statements。

### 写法和适用边界

- expect 必须紧随 insert、insert many、upsert、upsert many、update 或 delete；空行和注释不打断相邻关系，查询或另一个 expect 会打断。
- 支持 `== != < <= > >=` 与非负整数常量；不接受 `expect affected = 1`、参数或任意布尔断言。至少命中一行可写 `expect affected >= 1`。
- 守卫检查命中行数，不自动证明余额、权限或其他领域规则。规则应写入 filter 并在应用中维护。
- memory 和 redb 支持守卫；旧 WAL/snapshot 模式返回 E_CONFIG，持久业务数据使用 `--db`。
- 一个新脚本最多 4,096 条顶层语句，摘要最多 512 KiB，预算在提交前检查。批量数据使用 insert many，不逐行堆叠数千条语句。
- UnionID 面向单机、一个数据库所有者与串行写入；约 10,000 行是当前舒适工作集，100,000 行为已测试上限。这个版本没有新增分布式事务或吞吐承诺。

### 从 v0.11 升级

先为现有数据库做备份，再替换二进制并运行 `version`、`check --db <path>` 和应用查询回归。v0.11 → v0.12 无需内部格式升级或应用 schema migration：默认 storage 10，可读 1–11；backup 6，可读 1–6；protocol 1/2 和 stream 1 保持不变。

Rust 应用将 unionid、unionid-derive、unionid-query 统一升级为 0.12.0。直接构造公开 struct literal 时，新增的 Error.statement_index 和 response.statements 字段需要初始化；旧 serde payload 使用默认值仍可读。维护或还原带新摘要的幂等回执使用匹配版本，旧程序重写可能丢弃未知元数据。详见 [升级说明](https://github.com/worktools/unionid/blob/v0.12.0/docs/UPGRADING.md)。

v0.12 保留 v0.11 的本地 Parquet 入口：`unionid parquet file.parquet --query 'from data | filter active'`；它是只读外部数据查看，不提供这个版本的原子写入。见 [Parquet 文档](https://github.com/worktools/unionid/blob/v0.12.0/docs/PARQUET.md)。

## English Description

### What this release does for an application

[Get v0.12.0](https://github.com/worktools/unionid/releases/tag/v0.12.0). UnionID is a single-machine Rust database for application state, with struct/enum data, typed pipelines, and redb persistence. This version makes an affected-row requirement part of one atomic request. Use it to claim pending tasks, update a specific configuration version, or require both steps of a business write to succeed. Zero-row updates remain valid unless you add a guard.

### Install and try it

Native archives support Linux x86_64 and Apple Silicon macOS and include documentation, examples, and checksum files. Verify the published SHA-256, extract your platform's archive, and add its bin directory to PATH. With Rust 1.94 or newer:

```bash
cargo install unionid --version 0.12.0 --locked
unionid version --format json
unionid docs query
```

Confirm software_version is 0.12.0. The bundled query reference includes atomic-claim and can be provided to an LLM. For a generated project with migrations, follow the [five-minute guide](https://github.com/worktools/unionid/blob/v0.12.0/docs/GETTING_STARTED.md).

In a fresh experiment directory, save this as `setup.unid`:

```unid
enum State {
  Pending
  Running {worker: text}
  Done
}
struct Job {id: int, state: State, version: int}
table jobs: Job {key id}
insert jobs {id: 1, state: Pending, version: 0}
```

Save the claim as `claim.unid`:

```unid
update jobs
filter id == 1 && version == 0 && state == Pending
set {
  state = Running {worker: "worker-1"}
  version = version + 1
}
returning {id, state, version}
expect affected == 1
```

```bash
unionid run --db jobs.redb --file setup.unid
unionid run --db jobs.redb --file claim.unid --format json
unionid run --db jobs.redb --query 'from jobs' --format json
```

The first claim returns ok=true, affected_rows=1, and the Running row with worker-1/version 1. The trailing guard preserves returning rows. The statements array contains update at index 1 with affected_rows=1 and expect at index 2. Because the field type is known, Pending/Running may omit the State:: prefix.

Repeat the claim command. It fails with E_EXPECTATION, statement_index=2, and CLI exit code 3 because the original state/version no longer matches. Querying again shows worker-1/version 1 unchanged. Applications should bind task IDs, expected versions, and workers as prepared parameters rather than interpolate user input.

### Verify rollback across two writes

Save the following as `accounts.unid`. Integer balances represent smallest units for this demonstration, not a complete financial model.

```unid
struct Account {id: int, balance: int}
table accounts: Account {key id}
insert many accounts [{id: 1, balance: 100}, {id: 2, balance: 0}]
```

Save this as `transfer.unid`:

```unid
update accounts
filter id == 1 && balance >= 50
set balance = balance - 50
expect affected == 1

update accounts
filter id == 99
set balance = balance + 50
expect affected == 1
```

```bash
unionid run --db accounts.redb --file accounts.unid
unionid run --db accounts.redb --file transfer.unid --format json
unionid run --db accounts.redb --query 'from accounts | sort id'
```

The missing recipient fails the second guard at statement_index=4. Both balances remain 100 and 0: the candidate debit is rolled back with the request. Change recipient 99 to 2 and submit the entire transfer file again; both balances become 50 and the ordered summaries report both updates and guards.

**One request is the atomic boundary.** Do not split debit and credit into separate CLI invocations, network requests, or separately submitted REPL inputs. A later failure cannot undo a previously committed request.

### Integrate, retry, and interpret results

Embedded Rust applications can use Engine::prepare/execute_prepared with typed $sender/$recipient/$amount parameters. Static bindings and inline queries! macros accept one DML plus a trailing guard; use Engine/prepare or a full CLI/TCP/HTTP request for multiple writes. See [application data](https://github.com/worktools/unionid/blob/v0.12.0/docs/APPLICATION_DATA.md) for native Rust ADT binding and decoding.

A timeout or disconnected response does not prove rollback: the request might have committed. For safe retries, assign a stable idempotency_key to the business operation and retain the same query, parameters, and protocol version. request_id may change between attempts. A repeated key/digest replays the original result and summaries; different content conflicts, and failed requests do not occupy the key. Generating a fresh key for every attempt cannot prevent duplicated effects after a lost response.

| Result | Application action |
| --- | --- |
| ok=true | Read returning/final-query rows and per-operation counts from statements |
| E_EXPECTATION | The entire script rolled back; locate the guard using statement_index and re-read state before deciding on a new operation |
| E_EXPECTATION_CONTEXT | Fix the guard's position instead of retrying unchanged source |
| No complete response | Resolve possibly committed effects using the original idempotent request |

statement_index is one-based and counts top-level statements, not filter/set/returning stages. Failed scripts expose no uncommitted rows or summaries. A final query owns top-level rows; top-level affected_rows is not the total count across a script. Inspect statements for that information.

### Syntax and boundaries

A guard must immediately follow insert, insert many, upsert, upsert many, update, or delete. Blank lines/comments preserve adjacency; a read or another guard breaks it. Operators are ==, !=, <, <=, >, >= with a nonnegative integer literal. A single =, parameters, and arbitrary Boolean assertions are unsupported; use expect affected >= 1 for at least one match.

Guards prove cardinality, not authorization or complete business rules. Put row predicates in filter and maintain domain rules in your application. Guards work in memory/redb; legacy WAL/snapshot returns E_CONFIG, so use --db for persistent business data. A new script is limited to 4,096 top-level statements and 512 KiB encoded summaries, checked before commit. Use insert many for bulk data.

The product targets a single machine, one database owner, and serialized writes. Roughly 10,000 rows remain the comfortable working set; 100,000 rows are a tested upper bound. This version adds no distributed transaction or throughput guarantees.

### Upgrade from v0.11 and find help

Back up existing databases, replace the binary, then run version, check --db <path>, and application query regressions. v0.11 → v0.12 requires neither an internal format upgrade nor an application schema migration. Default storage remains 10/readable 1–11, backup 6/readable 1–6, protocol 1/2, and stream 1.

Keep unionid, unionid-derive, and unionid-query on 0.12.0 together. Direct public Rust struct literals need the new Error.statement_index or response.statements fields; old serde payloads retain default compatibility. Use matching binaries to maintain/restore receipts with new summaries, as old binaries may discard unknown metadata when rewriting. See [upgrading](https://github.com/worktools/unionid/blob/v0.12.0/docs/UPGRADING.md).

The v0.11 local Parquet viewer remains available through unionid parquet file.parquet --query 'from data | filter active'. It reads external data and does not support atomic mutations. See [Parquet](https://github.com/worktools/unionid/blob/v0.12.0/docs/PARQUET.md).

Offline references: unionid docs query, unionid docs show upgrading, and unionid agent --format json. Online: [query language](https://github.com/worktools/unionid/blob/v0.12.0/docs/QUERY.md) and [protocol/idempotency](https://github.com/worktools/unionid/blob/v0.12.0/docs/PROTOCOL.md). Native packages include examples/atomic_claim.unid and tutorial/validate-atomic-writes.py.

Both native platforms passed release acceptance, including published v0.11 compatibility, guard rollback, and receipt replay through restart/backup/journal recovery; see [acceptance evidence](https://github.com/worktools/unionid/issues/416).
