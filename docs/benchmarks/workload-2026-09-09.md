# M6 工作负载成本 / M6 workload cost · 2026-09-09

## 目的与工作负载

本次测量在增量 row-only DML 与有序复合索引实现后，重新记录 unionid 的 open、查询、持久写入和深层 migration 成本。数字用于确定当前舒适工作集与已测试上限，不是延迟或容量 SLA。

数据集使用命名 `Task` record 与命名 `State` sum，包含 tenant、priority、text/list、record variant payload 和 score。表有主键、两个单列索引，以及 `create index tasks (tenant, -priority, id)`。有序查询固定一个 tenant，读取 25 行；range、ordered scan 和前后向续页必须先通过结构化 `explain` 断言，才会进入计时。

写入覆盖主键条件 update、已有主键 upsert 和包含 100 条 insert 的原子脚本。migration 重命名并扩展嵌套 sum variant、为所有行回填新字段，并创建新索引，因此仍走完整 schema/data rebuild。

## 环境与方法

- 代码：#174 的复合索引格式、#175 的 range/order/page-seek planner，以及 #166 的 workload-eval 改动
- 构建：Rust 1.94.0，`--release --locked`
- 主机：MacBook Pro (MacBookPro18,3)，Apple M1 Pro，8 logical CPUs，16 GiB memory
- 系统：macOS 26.6.2 (25G83)，arm64
- 样本：每个 case 20 个；query/write 在 5 次 warm-up 后计时，open/migration 每次使用独立数据库副本和子进程

```bash
cargo run --release --locked --manifest-path tools/workload-eval/Cargo.toml -- /tmp/unionid-workload-10k.redb 10000 20 1500
cargo run --release --locked --manifest-path tools/workload-eval/Cargo.toml -- /tmp/unionid-workload-100k.redb 100000 20 1500
```

源码生成、数据库复制、cursor 构造、结构化计划断言、结果检查和完整性检查不计入 elapsed sample。每个子进程仍会打开完整 resident Engine，因此 peak RSS 包含该 case 的数据库常驻状态。写入另外保留 candidate construction 与 durable commit 的分段样本。完整输出见 [10k JSON](data/workload-2026-09-09-10k.json) 与 [100k JSON](data/workload-2026-09-09-100k.json)；两者 schema revision/hash 均为 `1` / `sha256:e18d20347a884774bc4d017b99377d54940752aae2ca298645102428ad4b6fcb`。

写入 peak RSS：10k 的 update/upsert/batch 为 74.84/75.50/79.20 MiB，100k 为 664.98/670.03/672.95 MiB。migration 分别为 154.30 MiB 与 1,472.67 MiB。准备后的数据库大小为 16,846,848 bytes（16.07 MiB）与 134,746,112 bytes（128.50 MiB）。

与 [M5 基线](workload-2026-09-07.md) 相比，100k 单行 update/upsert p95 从约 0.88 秒降到约 10 毫秒，100-row batch 从约 506 毫秒降到 16 毫秒。candidate construction 已与总表行数基本脱钩，剩余约 9–14 毫秒主要是 redb durable commit。新数据集增加 tenant/priority 和第三个复合二级索引，因此数据库与常驻内存不能和旧数据集逐字节比较。

深层 migration 仍是 full rebuild，且 100k 的 durable commit 在这个更宽、索引更多的数据集上达到约 47.6 秒 p95。这是当前最明显的容量限制，说明增量 DML 的改善不能外推到 schema/data migration。

## 当前边界

约 10k 行仍是日常使用的舒适参考范围：indexed/ordered read 为微秒级，单行持久写入约 10 毫秒 p95，100-row 原子写入约 15 毫秒 p95，但深层 migration 约 0.95 秒。100k 只作为已测试上限：普通有界读写保持稳定，完整打开约 5.6 秒，resident query 接近 1 GiB，深层 migration 约 50 秒并达到约 1.44 GiB peak RSS。

应用若接近 100k 行，应在部署前用自己的 value 宽度、索引数量、文件系统和 migration 复测，并为 maintenance 留出明确停机窗口。需要更大常驻数据集或频繁大 migration 的场景，仍需等待 streaming open/check 与增量 migration 工作。

## English summary

This rerun validates the M6 incremental-write and ordered-index paths with 20 retained samples per case. Structured plans are asserted before timing, and every child verifies row counts and redb/unionid integrity outside the timed interval.

At 100k rows, composite range, ordered scan, and resumed cursor pages remain in the 45–139 µs p95 range. Single-row update/upsert p95 falls from the M5 baseline of about 0.88 seconds to about 10 milliseconds, while a 100-row atomic insert falls from about 506 milliseconds to 16 milliseconds. Candidate construction is now proportional to the write set; durable redb commit dominates ordinary writes.

The resident engine still loads the complete typed working set. A 100k open takes about 5.6 seconds p95, query subprocesses approach 1 GiB RSS, and a full deep migration takes about 49.9 seconds p95 with 1.44 GiB peak RSS. Keep roughly 10k representative rows as the comfortable operating reference and 100k as a tested ceiling rather than a routine target. These single-machine measurements are evidence, not an SLA.
