# M9 长期 churn 与 reclaim 证据 / M9 long-term churn and reclaim evidence

## 中文说明

### 范围与环境

本记录为 [#209](https://github.com/worktools/unionid/issues/209) 和 [#229](https://github.com/worktools/unionid/issues/229) 保存 format-6 长期 churn 证据。测量基于 `f29f911` 之后的 #229 分支，使用同一个 release 二进制、Apple M1 Pro（16 GiB）、macOS ARM64、8 logical CPUs、Rust 1.94.0、6 轮和固定 seed `20260910`。结果描述这台机器和固定工作负载，不是 SLA。

原始结果：

- [10k JSON](data/churn-10k-2026-09-10.json)
- [100k JSON](data/churn-100k-2026-09-10.json)

运行命令：

```bash
tools/churn-eval/target/release/unionid-churn-eval \
  /tmp/unionid-churn-evidence-10k 10000 6 20260910 500
tools/churn-eval/target/release/unionid-churn-eval \
  /tmp/unionid-churn-evidence-100k 100000 6 20260910 500
```

每轮组合单行 update/upsert/delete、批量 insert、幂等重放和有界 receipt prune，净增加一行。前三轮依次应用三代 shadow migration。第一代还在独立子进程中分别停在首个 1,024-row build batch、cutover 完成后和首个 reclaim batch 之后，再由普通 apply 重开并完成清理。每轮随后重开数据库、运行完整 check 和 logical backup，并把全部 typed rows、索引查询、schema、ledger、receipt 与独立参考模型比较。

QueryResponse 的 100,000 行上限会在 100k workload 第一轮后拒绝单次全量验证。runner 因此按参考主键边界使用最多 10,000 行的无缝范围块，逐行验证完整有序结果，并按行计算与单个紧凑 JSON 数组相同的逻辑字节数。它不会提高产品结果上限，也不会跳过多行、少行或值不一致检查。

### 结果

下表中的 p50/p95 使用 6 轮样本；RSS 是整个 release evaluator 进程的高水位，包含参考模型、查询结果、redb 映射和运行时，不能解释为单个 Engine 操作的 working set。

| 指标 | 10k | 100k |
| --- | ---: | ---: |
| 初始／最终行数 | 10,000 / 10,006 | 100,000 / 100,006 |
| 首次 migration 前文件 | 12.00 MiB | 96.00 MiB |
| 首次 migration 后文件 | 46.13 MiB | 745.21 MiB |
| 第 6 轮文件 | 45.98 MiB | 744.84 MiB |
| 第 6 轮 logical rows | 5.22 MiB | 52.27 MiB |
| logical / file | 11.35% | 7.02% |
| open p50 / p95 | 3.94 / 4.05 ms | 3.85 / 4.01 ms |
| full check p50 / p95 | 279.94 / 283.09 ms | 2.86 / 2.88 s |
| logical backup p50 / p95 | 417.88 / 429.37 ms | 4.11 / 4.16 s |
| evaluator peak RSS | 205.23 MiB | 1,840.41 MiB |

10k 的三次完整 migration 为 1.14–1.32 s。100k 为 13.49–25.84 s；带三个强制退出点的第一代最慢，其中 build 5.62 s、validate 2.51 s、cutover 9.10 ms、reclaim 17.51 s。后两代 build 为 5.90–6.25 s、validate 为 2.45–2.97 s、cutover 小于 9 ms、reclaim 为 5.12–5.32 s。

两种规模都完成全部六轮。第一代的三个 checkpoint 保留 `building` 和 `reclaimable` 状态，最终 maintenance state 清空；三代 ledger 各追加一次，没有重复。最终 schema revision/hash 都为 `4` / `sha256:7555e4fe04584c1da4c905b98464600eaa2b9a6d2ed7b0604a5d5f7d5a1b34f0`。最终参考摘要分别为 `sha256:9a24f3296ac15418caaf8953900173323dffaa07040523192ce7e0bc049319cd` 和 `sha256:9e4fd8bfbdbd8f5e7aa81b9df12a35b72158efa54aa166c64be0cf511eb7eae4`。

### 使用结论

- Reclaim 在逻辑上完整删除旧 generation，后续 migration 和三轮普通 churn 没有继续扩大文件；10k/100k 从第一轮到第六轮分别减少约 0.15/0.36 MiB。redb 文件不会随逻辑删除自动收缩，因此第一次 shadow migration 把 100k 文件从 96.00 MiB 推到约 745 MiB 后维持高水位。运维容量必须同时考虑 source、shadow generation、索引和 redb 已分配空间，不能只按 logical backup 大小估算。
- 约 10k 行仍是更舒适的日常范围。100k 能完成重复写入、三代 migration、强制中断恢复、check 和 backup，但完整 migration、全库维护、约 745 MiB 文件和约 1.80 GiB evaluator RSS 都有明显成本，应继续作为已测试上限。
- 应用在接近 100k 时应先在静止的生产副本上运行完全相同的 migration 和 churn，保留 verified logical backup，并为 build、reclaim 和文件高水位预留维护窗口与磁盘空间。物理压缩或文件重写由 [#230](https://github.com/worktools/unionid/issues/230) 独立设计，不能把 generation reclaim 当作 vacuum。

## English Description

### Scope and environment

This record retains format-6 long-term churn evidence for [#209](https://github.com/worktools/unionid/issues/209) and [#229](https://github.com/worktools/unionid/issues/229). Both sizes used the same release binary from the #229 branch based on `f29f911`, an Apple M1 Pro with 16 GiB RAM, macOS ARM64, 8 logical CPUs, Rust 1.94.0, six rounds, and seed `20260910`. The results characterize this host and fixed workload and are not an SLA. Raw results are retained in the linked [10k](data/churn-10k-2026-09-10.json) and [100k](data/churn-100k-2026-09-10.json) JSON files.

Each round combines single-row update/upsert/delete, batch insert, idempotent replay, and bounded receipt pruning, for a net increase of one row. The first three rounds apply a three-generation shadow-migration chain. Generation one also exits separate child processes after the first 1,024-row build batch, after cutover, and after one reclamation batch before an ordinary apply reopens and completes cleanup. Every round then reopens the database, runs a full check and logical backup, and compares all typed rows, indexed probes, schema, ledger, and receipts with an independent reference model.

A single complete validation exceeds the 100,000-row QueryResponse limit after the first 100k churn round. The runner therefore partitions the complete primary-key domain into contiguous ranges of at most 10,000 expected rows, validates every ordered row, and computes the exact compact-array logical byte count incrementally. This does not raise the product result limit or omit extra, missing, or mismatched rows.

### Results

| --- | ---: | ---: |
| Initial / final rows | 10,000 / 10,006 | 100,000 / 100,006 |
| File before first migration | 12.00 MiB | 96.00 MiB |
| File after first migration | 46.13 MiB | 745.21 MiB |
| Round-six file | 45.98 MiB | 744.84 MiB |
| Round-six logical rows | 5.22 MiB | 52.27 MiB |
| Logical / file | 11.35% | 7.02% |
| Open p50 / p95 | 3.94 / 4.05 ms | 3.85 / 4.01 ms |

| Logical backup p50 / p95 | 417.88 / 429.37 ms | 4.11 / 4.16 s |
| Evaluator peak RSS | 205.23 MiB | 1,840.41 MiB |

The three complete 10k migrations take 1.14–1.32 seconds. The 100k migrations take 13.49–25.84 seconds. The first generation includes all three forced exits and is the slowest: build takes 5.62 seconds, validation 2.51 seconds, cutover 9.10 milliseconds, and reclamation 17.51 seconds. The later generations spend 5.90–6.25 seconds building, 2.45–2.97 seconds validating, under 9 milliseconds cutting over, and 5.12–5.32 seconds reclaiming.

Both sizes complete all six rounds. The first generation retains the expected `building` and `reclaimable` checkpoints before ending with no maintenance state. Each of the three ledger entries appears exactly once. Both final schemas are revision `4` with hash `sha256:7555e4fe04584c1da4c905b98464600eaa2b9a6d2ed7b0604a5d5f7d5a1b34f0`. The final reference digests are `sha256:9a24f3296ac15418caaf8953900173323dffaa07040523192ce7e0bc049319cd` and `sha256:9e4fd8bfbdbd8f5e7aa81b9df12a35b72158efa54aa166c64be0cf511eb7eae4`.

### Operational conclusions

- Reclamation logically removes the old generation, and the later migrations plus three ordinary churn rounds do not keep growing the file. The 10k and 100k files shrink by about 0.15 and 0.36 MiB between rounds one and six. Redb does not automatically shrink its file after logical deletion, so the first shadow migration raises the 100k file from 96.00 MiB to about 745 MiB and leaves that allocation as a high-water mark. Capacity planning must include the source, shadow generation, indexes, and redb allocation rather than using logical-backup size alone.
- Around 10k rows remains the more comfortable everyday range. The 100k run completes repeated writes, three migrations, forced interruption recovery, checks, and backups, but complete migration time, full-database maintenance, the roughly 745 MiB file, and roughly 1.80 GiB evaluator RSS are material costs. It remains a tested ceiling.
- Near 100k, rehearse the exact migrations and churn workload on a quiescent production-data copy, retain a verified logical backup, and reserve a maintenance window and disk headroom for build, reclamation, and the file high-water mark. [#230](https://github.com/worktools/unionid/issues/230) tracks the separate physical-compaction design; generation reclamation is not a vacuum operation.
