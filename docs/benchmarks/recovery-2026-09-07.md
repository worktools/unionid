# Recovery cost · 2026-09-07

## Purpose

This measurement bounds the current cost of loading and validating a durable unionid database. It is not a general query benchmark or a latency guarantee.

The workload uses named `Task` and `State` ADTs, record and sum payloads, list/text fields, a primary key, and secondary indexes over the sum value and title. Rows are written in atomic batches of 3,000. Preparation runs separately from each measured child process.

## Environment

- Commit under test: `b530c05` plus the recovery-eval change in this PR
- Build: Rust/Cargo 1.94.0, `--release --locked`
- Host: MacBook Pro (MacBookPro18,3), Apple M1 Pro, 8 cores, 16 GiB memory
- OS: macOS 26.6.2 (25G83), arm64
- Samples: three fresh databases per size; table reports the median

## Commands

```bash
cargo run --release --locked --manifest-path tools/recovery-eval/Cargo.toml -- /tmp/unionid-recovery-10k.redb 10000
cargo run --release --locked --manifest-path tools/recovery-eval/Cargo.toml -- /tmp/unionid-recovery-100k.redb 100000
```

Each invocation creates a new database, verifies its row count, then starts separate `measure-open` and `measure-check` child processes. `open` includes redb open, catalog/row decoding, schema/ledger/RowId validation, and complete derived-index verification. `check` measures `Engine::check_integrity` after the process has opened the database; this runs redb integrity checking, reloads, and repeats unionid logical validation. Peak RSS is sampled immediately after each measured operation and before the post-operation row-count assertion. It comes from `getrusage(RUSAGE_SELF)` and is normalized to bytes on macOS and Linux.

## Median results

| Rows | Database | Prepare | Open | Open peak RSS | Full check | Check peak RSS |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10,000 | 8,421,376 B (8.03 MiB) | 380 ms | 66 ms | 55,230,464 B (52.67 MiB) | 78 ms | 85,442,560 B (81.48 MiB) |
| 100,000 | 134,737,920 B (128.50 MiB) | 10,053 ms | 653 ms | 481,591,296 B (459.28 MiB) | 741 ms | 782,073,856 B (745.84 MiB) |

All six open runs and all six checks recovered the expected typed row count and passed catalog, schema hash, migration ledger, RowId, primary-key, and secondary-index validation.

## Product boundary

The 10,000-row case fits the intended small application-state workload comfortably on this machine. The 100,000-row case remains below one second for open and full check, but full checking peaks near 0.75 GiB because the current Engine loads the complete typed working set and reconstructs validation state. Treat 100,000 rows as a tested ceiling for v0.1 rather than a routine memory target. Applications that need substantially larger resident datasets should wait for streaming recovery and incremental validation work.

These results do not simulate physical power removal, a filesystem that violates synchronization guarantees, or damaged hardware. They complement the macOS/Linux process-exit and real file-growth failure tests in `tests/storage.rs`.
