# Workload cost · 2026-09-07

## Purpose

This measurement records query, durable write, and schema/data migration costs for the current small application-state engine. It complements the separate [open/check recovery measurement](recovery-2026-09-07.md); it is not a latency guarantee.

The workload stores named `Task` records with a named `State` sum, record variant payloads, list/text fields, an integer score, a primary key, and secondary indexes over state and title. The migration renames `Running` to `Claimed`, adds an optional lease to its payload, backfills priority on every task, and creates a priority index.

## Environment and command

- Commit under test: `d226e91` plus the workload-eval change in this PR
- Build: Rust/Cargo 1.94.0, `--release --locked`
- Host: MacBook Pro (MacBookPro18,3), Apple M1 Pro, 8 cores, 16 GiB memory
- OS: macOS 26.6.2 (25G83), arm64
- Samples: 20 measured iterations after five warm-ups for query/write cases; 20 fresh database copies and child processes for migration

```bash
cargo run --release --locked --manifest-path tools/workload-eval/Cargo.toml -- /tmp/unionid-workload-10k.redb 10000 20 3000
cargo run --release --locked --manifest-path tools/workload-eval/Cargo.toml -- /tmp/unionid-workload-100k.redb 100000 20 3000
```

The tool prepares one closed template database, copies it outside timed intervals, and runs every case in a release child process. Source generation, explain assertions, warm-up, copies, and typed-result checks are excluded from elapsed samples. Peak RSS includes database open and warm-up state for that case. Migration has no warm-up: every sample opens and migrates a fresh copy, with only the atomic migration execution timed.

Nearest-rank percentiles are calculated from the retained microsecond samples. The complete outputs are stored as [10k JSON](data/workload-2026-09-07-10k.json) and [100k JSON](data/workload-2026-09-07-100k.json).

## Interpretation and boundary

Primary and secondary equality lookups stay essentially constant because the typed planner uses the expected index. The controlled unindexed predicate scales with the resident row count. These access paths are asserted through structured `explain` before measurement rather than inferred from elapsed time.

Every durable mutation currently clones the complete in-memory database to stage an atomic request, then computes and commits stable-key differences. A 100-row batch amortizes that fixed work better than a single-row update. The same candidate-state model plus full nested-row conversion and index rebuild dominates migration. This behavior is deliberate for easy-to-audit small workloads, but it makes 100k-row writes approach one second and about 1.25 GiB peak RSS on this machine.

Treat roughly 10k representative rows as the comfortable current operating range and 100k as a tested ceiling for v0.1. Workloads that need frequent writes or migrations near 100k rows should wait for copy-on-write candidate state and streaming/incremental migration work. The exact boundary depends on value size, indexes, hardware, filesystem, and concurrent application memory.
